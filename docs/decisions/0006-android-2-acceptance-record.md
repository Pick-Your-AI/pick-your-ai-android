## Decision and alternatives

Place **only Android #2 / epic 01** in this Android repository at the same relative
path, preserving the original website location as history. The integrated record
links the six delivered child outcomes, their actual owners/reviews, the concrete
decision demonstration and all four literal parent criteria.

Keeping this new record in the website would separate it from all six accepted
Android decision records and involve a repository whose main merges deploy the
website. Duplicating it would create competing parent receiving authorities. One
reviewed Android record keeps the decision chain together while preserving the
canonical website service package and research/Apple acceptance ownership.

The child documents are not moved again or rewritten. No website file is copied,
replaced or deleted. This ADR changes no service location, application framework,
frozen format, source-use rule, implementation ownership, native hierarchy or
Project field. Every other unmoved record retains its existing placement gate.

## Review and strict acceptance transition

The required product decision authority and Android technical lead review must
assess the full integrated artifact, accepted child/handoff pins, actual desk
demonstration, conditional scope and unresolved implementation/operating evidence.
Record the exact independent agent review truthfully; it is not a participant,
physical-device, live-service or human operating acceptance result.

This document delivery changes no criterion ledger, validator or adversarial
test. After normal signed delivery and exact default-branch verification, use the
then-canonical strict current schema for the separately reviewed epic acceptance
record. Reuse its versioned history and exact evidence mechanism rather than
creating a competing index or weakening its guard.

Bind only the four original #2 criteria to the delivered reviewed record and
receiving receipt. Preserve every literal ID/text/digest, prior partial evidence,
old result, historical repository/path, all child receipts and every other issue
object. The currently accepted children do not automatically complete the parent.
Only the subsequent complete, reviewed and delivered acceptance reconciliation
permits intentional parent metadata changes. Program, application, device,
factual, service and release acceptance remain their own scopes.
