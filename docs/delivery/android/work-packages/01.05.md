# Android 01.05 / #25: guest, accounts and revenue decisions

Decision date: 2026-10-18. Issue: [Android #25](https://github.com/Pick-Your-AI/pick-your-ai-android/issues/25).
Prepared under the maintainer's explicit delegation of project product and
engineering decisions. This decision takes effect through independent product/

## Selected baseline

Enable free guest-local planning for the first bounded Android slice. A person
can plan, acknowledge a local save and return to their own retained draft without
registering, supplying a provider credential, consenting to optional collection
or buying access. Keep the [accepted J1–J4 scope](01.02.md); J5 file exchange and
remote sharing remain conditional later. Free access to the planning client does
not make the selected model, hardware or provider free: cost coverage and unknown
rates retain their canonical research #39 requirements.

Do not enable account creation, external signup links, cloud synchronization,
paid downloads/plans, purchases, subscriptions, referrals, advertising,
personalization, optional analytics, automatic crash upload or notifications in
this baseline. The table below gives each capability its own rationale and
activation conditions. This is an explicit initial scope decision, not a claim
that the product will always be free or that these services are implemented.

Preserve local, explicitly reviewed diagnostics and source-version context as
engineering work under #33/#44. Any transfer still requires the person's
deliberate action and exact payload preview; it is not optional telemetry silently
enabled by this decision. An unavailable support destination must say unavailable.
The [diagnostic implementation delivered at 74fac80d](https://github.com/Pick-Your-AI/pick-your-ai-android/blob/74fac80d69c62e1e2de3cc2a6884aa51f763dbcc/docs/LOCAL_DIAGNOSTICS.md)
remains its own bounded delivery; its support destination is explicitly unavailable.

## Authority, upgrade and data lifecycle

Local drafts are app-private working records, not app accounts, public identifiers
or ownership credentials. Select retention until the user explicitly deletes the
draft/history or clears app data, subject to the existing documented storage
limits and recoverable errors. Do not silently discard acknowledged work to
satisfy a quota. The source backup exclusions require actual supported-device
qualification; "local" is not a guarantee about OS transfer, keyboard services,
screenshots, an unlocked device or copies deliberately exported elsewhere.

For any later remote capability, accept these requirements through the canonical
#35/#62 and website #17 lane before collection or implementation activation:

1. The server checks the caller's scoped authority for every private read and
   mutation. Random resource IDs, client-supplied ownership and Android App Link
   verification do not provide it. Guest write authority must be securely issued
   and kept separate from a public viewer capability.
2. A viewer gets only the approved immutable read projection. Viewer authority
   cannot list private history, update, fork as the owner, delete or revoke.
   Define scope, expiry, revocation, abuse limits and cache consistency; reject
   expired, forged or unrelated authority without leaking private object details.
3. Bind idempotency, revision comparison and pending operations to the correct
   principal and object. Lost acknowledgments need reconciliation; retries cannot
   create duplicate revisions or cross-identity results. Logout/revocation/
   deletion must prevent queued operations from restoring inaccessible data.
4. A future upgrade requires a deliberate authenticated step and explicit choice
   of which local or guest-owned records to transfer. Prove both the current guest
   authority and the new account authority where ownership changes. Declining or
   canceling preserves local use; signing in alone uploads nothing.
5. Keep account, creator and write credentials out of URLs, exports, planning
   records and diagnostics. A public viewer link conveys only its approved read
   projection and never includes those private powers.
   Choose actual custody, recovery and service retention with the responsible
   implementation lane. If guest authority is lost, do not invent an account
   recovery path or accept an asserted owner ID as proof.
6. Distinguish local deletion, a remote deletion request, confirmed server
   deletion and link revocation. Define backup/service-provider retention and
   disclosed exceptions before activation. Deleting a local original cannot
   recall recipient copies. Failed or pending deletion must remain visible;
   removing a local index entry cannot be reported as remote erasure.

These are receiving requirements, not new frozen-v1 fields, wire tokens or
endpoints. Preserve research #40 versioning, #42 lifecycle semantics, #41
evidence/freshness and #60 exact source-use rights. This decision chooses no
hosting vendor, deployed database, identity provider, operator or retention SLA.
